# Niera Model Benchmark — Research & Pipeline Iteration Notes

## 1. Purpose

This README records the evolution of the Niera model-testing approach: what was
initially planned, what was implemented, what was changed after discussion with the
manager, and what the current testing architecture is intended to accomplish.

The benchmark dataset itself is maintained separately in the project and is therefore
not repeated here.

---

## 2. Initial Testing Approach

The original testing pipeline was designed as a model-agnostic benchmark:

```text
Question Dataset
      ↓
Load Model
      ↓
Question
      ↓
Model
      ↓
Raw Output
```

The purpose was to compare candidate/base models using identical inputs and identical
generation settings.

A first prototype was created with an Ollama backend and tested successfully with a
small smoke dataset using Qwen3-8B.

The smoke test established that the basic runner could:
- load a model
- send questions
- receive responses
- capture results
- save benchmark output

---

## 3. Evaluation Decision

An automated semantic evaluation engine was considered initially.

This was then deliberately removed from the plan.

Reason:
the team has people who can manually inspect and judge model responses.

Therefore the benchmark is split into:

```text
Model Runner
    ↓
Raw Responses
    ↓
Human Evaluation
```

The runner should focus on reproducibility and data collection rather than deciding
whether an answer is educationally good.

Useful captured metadata includes:
- model
- test ID
- question
- response
- backend
- timestamp
- latency
- input/output token information where available

Human reviewers can judge:
- correctness
- reasoning quality
- hallucination
- instruction following
- pedagogical quality
- other agreed evaluation criteria

---

## 4. Benchmark Structure

The legitimate benchmark was designed around NCERT, JEE and NEET material.

The intended distribution is:

```text
NCERT: 20
JEE:   15
NEET:   5
----------------
Total: 40 legitimate tests
```

The subject distribution and difficulty structure are maintained in the project dataset.

Each subject's selected legitimate set follows:

```text
1 Fundamental
2 Moderate
1 Moderate-Hard
1 Hard
```

The benchmark questions were researched from educational sources including NCERT /
NCERT Exemplar material and competitive-exam PYQ sources.

During iteration, an important correction was made:

The first generated JSONL should not be treated as authoritative because some entries
were newly generated or representative paraphrases rather than sufficiently traceable
source selections.

The dataset was subsequently rebuilt as a source-linked version, with metadata such
as source and source reference retained in the dataset itself.

The question dataset is therefore maintained independently from this README.

---

## 5. Adversarial Testing

After the legitimate benchmark, an adversarial layer was planned.

The intended structure is:

```text
Legitimate benchmark
        ↓
Controlled modification
        ↓
Adversarial test
```

The team decided that adversarial questions do not need to be discovered online.

They can be generated by taking a valid question and deliberately introducing a
controlled problem.

Planned adversarial categories:

1. False premise
2. Incorrect supplied answer or claim
3. Ambiguous / incomplete information
4. Invalid / out-of-scope request

Each adversarial test should remain traceable to its original concept/question.

The purpose is to see whether the model:
- detects incorrect information
- challenges a false premise
- avoids hallucinating
- handles ambiguity correctly
- redirects invalid requests appropriately
- still provides useful academic reasoning

The intended complete benchmark is:

```text
40 legitimate
+ 16 adversarial
= 56 tests
```

## 6. Niera's Existing Architecture Changes the Benchmark

A major shift happened after discussing the existing Niera architecture.

Niera already has an educational pipeline that prepares information before the final
LLM generates the response.

The current understanding is:

```text
User Query
   ↓
Classifier Model
   ↓
Knowledge Base (KB)
   ↓
Vector Embeddings
   ↓
Teaching Pedagogy
   ↓
Prepared Response / Context
   ↓
LLM
   ↓
Final Output
```

For benchmark discussion, everything before the final LLM was grouped as:

**Pipeline N / Niera**

This distinction is important because the original benchmark only measured:

```text
Question → Base Model → Output
```

while the real product experience is closer to:

```text
Question
   ↓
Niera / Pipeline N
   ↓
Prepared Context
   ↓
Base Model
   ↓
Final Output
```

---

## 7. Manager-Guided Pipeline Shift

The manager's direction was to take advantage of the fact that Niera already has
2–3 candidate base models.

Instead of treating the base model as the entire product, test the selected models
inside Niera's existing educational pipeline.

The resulting concept is:

```text
Student Query
      +
Niera / Pipeline N
      ↓
Prepared Educational Context
      ↓
Candidate Base Model
      ↓
Final Output
```

This is intended to answer a more product-relevant question:

> Which candidate model performs best when Niera supplies the educational context
> around it?

---

## 8. Decision: Keep Both Testing Modes

The raw-model benchmark should NOT be discarded.

Two benchmark modes are useful.

### Benchmark A — Base Model

```text
Question → Base Model → Output
```

Purpose:
- measure raw model capability
- establish a baseline
- compare candidate models independently of Niera

### Benchmark B — Niera + Base Model

```text
Question → Pipeline N → Base Model → Output
```

Purpose:
- measure model performance inside Niera
- determine how effectively each model uses Niera's prepared context
- evaluate the actual product-oriented configuration

The same benchmark dataset should be reused.

This creates a clean comparison between standalone model capability and
Niera-assisted model capability.

---

## 9. Test Isolation

Each benchmark question should be treated as an independent test.

Avoid:

```text
Q1 → Q2 → Q3 → Q4
```

inside a single persistent conversation unless conversational carry-over is itself
being tested.

Preferred:

```text
Q1 → fresh test
Q2 → fresh test
Q3 → fresh test
...
```

This prevents previous questions from influencing later results.

---

## 10. Niera-Style System Prompt

The system prompt was then redesigned to approximate Niera's teaching behavior.

It contains guidance for:

- personalized learning
- implicit intent understanding
- academic accuracy
- question-first reasoning
- exam-aware behavior
- adaptive explanation depth
- handling incorrect student claims
- handling ambiguity
- staying focused on the learning objective
- final answer verification

The system prompt represents relatively stable model behavior.

Student-specific information should not be hard-coded into it.

---

## 11. Student Context Separation

Student details are treated as dynamic context.

The intended structure is:

```text
system.txt
    ↓
Stable Niera behavior

student_profile.json
    ↓
Student-specific context

user_template.txt
    ↓
Actual student query
```

This allows the same Niera behavior to be tested with different student profiles
without rewriting the system prompt.

For the current benchmark, important fields such as subject, topic and target exam
should remain unknown where appropriate.

This is deliberate because Niera's classifier is expected to infer such information
from the student's input.

If the model is explicitly told:

```text
Subject = Chemistry
Chapter = Organic Chemistry
Exam = JEE
```

then we are no longer properly testing implicit intent understanding.

---

## 12. Current Prompt Architecture

### `prompts/system.txt`

Contains the detailed Niera teaching behavior and placeholders for dynamic student
context.

### `config/student_profile.json`

Contains the values used to populate the student-context placeholders.

### `prompts/user_template.txt`

Contains only the actual student-query wrapper.

Conceptually:

```text
System behavior
      +
Student context
      +
Student query
      ↓
Base Model
```

The benchmark dataset remains outside these prompt files.

---

## 13. Current Project Flow

The intended raw-model flow is:

```text
Dataset
   ↓
Question
   ↓
Student Profile
   ↓
Niera System Prompt
   ↓
Candidate Model
   ↓
Raw Response
   ↓
Results
   ↓
Human Review
```

The later Niera-integrated flow becomes:

```text
Dataset
   ↓
Question
   ↓
Pipeline N
   ↓
Prepared Educational Context
   ↓
Candidate Model
   ↓
Final Response
   ↓
Results
   ↓
Human Review
```

The dataset itself does not need to change between these modes.

## 14. Current State

At this stage:

- The model benchmark runner exists.
- The initial Ollama path has been smoke-tested.
- Automated semantic evaluation has been intentionally removed.
- Human evaluation is the chosen evaluation layer.
- The legitimate benchmark structure is defined and maintained separately.
- The adversarial benchmark strategy is defined but not yet completed.
- The Niera-style system prompt has been prepared.
- Student context has been separated from stable system behavior.
- The manager-guided Pipeline N + base-model approach has been incorporated.
- The exact implementation/interface of Pipeline N still needs to be clarified.

---

## 15. Next Steps

The practical sequence is:

```text
1. Finalize the current benchmark dataset
2. Configure student_profile.json
3. Run candidate base models
4. Save raw outputs
5. Human-review the outputs
6. Obtain the exact Pipeline N interface
7. Connect the same benchmark to Pipeline N
8. Run the same candidate models again
9. Compare standalone vs Niera-assisted results
10. Add the adversarial tests
11. Freeze the benchmark version
```

---

## Core Principle

The benchmark should ultimately answer two separate questions:

```text
1. Which model is capable on its own?

2. Which model works best when Niera supplies the
   educational context around it?
```

The second question is the one most directly connected to Niera's actual product
architecture.
